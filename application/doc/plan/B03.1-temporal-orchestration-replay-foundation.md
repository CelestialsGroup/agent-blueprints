## Workflow And Transaction Boundaries

The implementation must preserve these boundaries:

1. The integration harness derives the stable Workflow identity from an already
   persisted Tenant-qualified WorkOrder and allocates the Platform WorkflowRun
   identity before Start. Caller-supplied native execution identity is rejected;
   the equivalent production caller remains blocked on persisted start-intent
   authority.
2. Temporal Start is network I/O and occurs outside every PostgreSQL
   transaction. Duplicate starts must resolve to the existing compatible
   execution; a conflicting workflow type, definition, or WorkOrder binding
   fails closed.
3. A timeout or lost Start response is an unknown outcome, not a failed start.
   Reconciliation resolves the stable identity from Temporal before any retry
   can create or confirm a Platform WorkflowRun.
4. Only confirmed or reconciled start evidence enters the PostgreSQL
   start-confirmation transaction. That transaction locks the WorkOrder,
   verifies Tenant and non-terminal eligibility, and appends exactly one
   immutable WorkflowRun. Same ID and digest replays return the existing
   result; any different binding conflicts.
5. Start failure before confirmation leaves no WorkflowRun. Continue-as-New
   segments and Worker retries never create another Platform WorkflowRun.
6. Workflow code schedules Activities and Timers only through Temporal APIs.
   Activities own PostgreSQL or external I/O, use bounded timeouts and explicit
   retry policies, and remain idempotent under at-least-once execution.
7. B03.1 does not update WorkOrder state because the required Canonical Event
   transaction is not representable with the current bounded parent facts.
8. RootBinding remains absent. No zero value, nullable owner string, test-only
   foreign key, or fabricated RunManifest may stand in for Root Admission.

The adapter-private native execution reference may be used transiently for
reconciliation, but only its Contract-governed digest is persisted in the
stable WorkflowRun binding.

## Worker Versioning And History Policy

- Workflow type names and Activity names are stable constants with explicit
  ownership.
- Every Worker uses an immutable Build ID and declared Versioning Behavior.
- Workflow definition changes require either deterministic compatibility,
  Temporal patching, or a new workflow version; code deletion must not break
  committed History fixtures.
- Old Worker builds remain available until every pinned execution is complete
  or migrated through an admitted compatibility path.
- Continue-as-New policy is explicit and based on bounded History criteria. A
  Continue-as-New segment preserves the Platform WorkflowRun identity.
- Workflow inputs and Activity results contain bounded control values only.
  Large data, user content, provider payloads, credentials, and endpoints are
  prohibited from History.
- Replay fixtures are sanitized, immutable after acceptance, source-bound, and
  contain no mutable production identifiers or secret material.

## Migration And Rollback Classification

The WorkflowRun migration is additive. Empty B03.1 tables may support a tested
Down followed by repeated Up. Once a WorkflowRun exists, rollback is forward
only unless an explicit compatibility migration preserves every immutable
binding and the old binary can read it. A rollback must never delete Temporal
History or reinterpret a confirmed start as absent.

Worker rollback retains the previous admitted Build ID and Workflow code until
Replay proves the target build compatible with all retained histories. New
builds are drained rather than replacing pinned executions in place. Temporal
SDK or Server rollback restores the prior reviewed pins only after Replay and
integration evidence; an engine data directory is never downgraded in place.
