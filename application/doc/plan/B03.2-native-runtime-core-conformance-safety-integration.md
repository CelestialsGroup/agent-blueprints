### B03.2a0 Native Runtime Durable Kernel

B03.2a0 is the first independently implementable slice. It contains only:

- an immutable Python configuration value and one ProviderRevision/Runtime
  revision binding per local state root;
- explicit packaged SQLite Up/Down migration, `foreign_keys=ON`, WAL,
  `synchronous=FULL`, bounded busy timeout, `STRICT` tables, and
  `BEGIN IMMEDIATE` write serialization;
- Provider-local Start, Status, bounded Command, cursor Event, user or exact
  reduction-only safety Pause/Cancel authority shape, `sandboxes=[]`, durable
  cancellation intent and later execution-loop cancellation evidence;
- atomic Start/Command JTI consumption, Start and Command digest idempotency,
  contiguous Command sequence, strictly increasing fencing, append-only typed
  Provider events with closed event-specific data values and fail-closed SQLite
  mapping, explicit expired cursor recovery, and retention only behind a usable
  checkpoint;
- a private execution-loop Port and recoverable leased work queue exercised by
  a bounded test executor;
- content-addressed checkpoint objects written temporary-file, digest/size,
  file `fsync`, atomic rename, directory `fsync`, then manifest/event
  transaction; restore is fail-closed outside exact `same_revision`.

The a0 API accepts domain values plus a `MutationAdmission` produced by a future
authenticated boundary. It does not parse HTTP, decode Strict I-JSON, validate
JWS headers/claims/signatures, authenticate mTLS identities, recompute Contract
request digests, or claim complete Start executable-context admission. Generated
transport values, `net/http`, PostgreSQL, Temporal, Provider discovery, signing
keys, and Platform authority do not enter the kernel.

B03.2a0 acceptance requires all of the following:

1. A repeated Start key plus digest consumes a fresh admitted JTI, returns the
   same RuntimeRun, and appends no duplicate event; a digest conflict consumes
   no JTI and creates no fact.
2. Command replay requires a fresh admitted JTI, while a new command requires
   the next sequence and a strictly higher fencing token. Conflicts and stale
   fencing consume no JTI.
3. `cancel_requested` remains non-terminal until the execution loop returns a
   durable evidence reference; only then may status become `cancelled` and emit
   `runtime.run.cancelled`.
4. Event reads use `event_sequence > after_event_sequence`; pruning without a
   checkpoint is rejected, and an older cursor returns explicit recovery facts.
5. Exact-revision checkpoint restore verifies ProviderRevision, Runtime
   revision, profile, digest, size, content reference, and bytes before
   execution dispatch. Compatible or portable restore is rejected.
6. Process/store reopen, expired work lease, and the crash window after object
   rename but before manifest commit recover the same RuntimeRun without a
   duplicate accepted mutation or event. An old lease owner cannot complete.
7. The locked Python artifact includes its migration resources; the Native
   Runtime test log and B03.2a0 evidence bind exact sources, dependency lock,
   Contract Manifest, Runtime Suite digest, and only the exercised kernel
   subsets.
8. The frozen quality environment pins `ruff==0.16.0`, `mypy==2.3.0`, and
   Python 3.14.6 standard-library `unittest`; the Gate passes Ruff format/lint,
   mypy strict checks over Native Runtime source/tests, all 23 tests, lock
   consistency, and reproducible wheel construction. Generated transport code
   remains governed by the separate zero-diff regeneration Gate.

## Native Runtime Component Design

### Process And Configuration

The process receives immutable startup configuration for ProviderRevision,
Runtime revision, Provider audience, trusted caller identities, verification
keys, Event Registry binding, checkpoint profile, local state root, body limits,
retention policy, concurrency limits, and bounded clock skew. Configuration
drift for one ProviderRevision fails startup or readiness; it must never change
the capabilities document in place.

The component test host may use the Python standard library HTTP/TLS stack if it
can prove the required boundary and graceful drain behavior. Selection of a
production server is outside B03.2a and requires its own dependency and capacity
review.

The local state root must use explicit permissions, avoid shared Tenant paths,
and contain no bearer token, private key, user credential, or Platform secret.

### Provider-Local Durable State

The initial store should use Python's standard-library SQLite and
content-addressed checkpoint objects. Its schema must distinguish at least:

- immutable Provider metadata and local schema version;
- RuntimeRun identity, immutable Platform bindings, current state, observed
  fencing token, last command sequence, last event sequence, timestamps, and
  optional terminal/checkpoint evidence;
- Start idempotency key, request digest, RuntimeRun binding, and replay outcome;
- append-only Command ID/digest, sequence, fencing, authority binding, JTI, and
  acceptance result;
- consumed mutation JTI values with expiry and operation binding;
- append-only typed events and the minimum retained event sequence;
- checkpoint manifest binding and content-addressed private payload metadata;
- recoverable execution-loop work and confirmed cancellation evidence.

Schema migration must be explicit. An empty store may support tested Down/Up;
after durable Runtime data exists, migration rollback is forward-only unless the
old binary has been proven to read the new state without reinterpretation.

### HTTP And Authentication Boundary

Capabilities uses authenticated mTLS according to the OpenAPI exception. Every
Run operation requires mTLS plus a compact JWS whose header, signature,
algorithm, key, type, audience, caller, lifetime, operation, Contract/profile,
request digest, execution IDs, immutable digests, and fencing binding are
validated before state is read or mutated.

The transport must:

- reject Start bodies above 8 MiB and Command bodies above 256 KiB before JSON
  parsing or Runtime work;
- require the exact content type, reject ambiguous duplicate fields, reject
  unknown fields through the generated boundary, and apply bounded response
  encoding;
- normalize Status and Event operation descriptors before digest validation;
- require execution authority for Start; use the Contract-defined
  safety-control authority restrictions for Status/Event and post-expiry
  reduction-only control;
- persist mutation JTI consumption atomically with the accepted mutation;
- reject redirect, alternate Host/audience, stale fencing, wrong path/body
  identity, and non-empty sandbox bindings for the no-Sandbox revision;
- return only Contract-shaped StandardError bodies and never log tokens, request
  content, checkpoint payloads, or private key material.

### State And Transaction Boundaries

1. Start validates transport, token, digest, executable context, authorization
   bindings, deadline, and `sandboxes=[]` before opening the store transaction.
   The transaction serializes on the Start idempotency identity, recognizes an
   exact replay, rejects a digest conflict, consumes the JTI, appends the Run and
   `runtime.run.started`, and commits before execution-loop work begins.
2. Command validation occurs before the transaction. The transaction locks the
   RuntimeRun through SQLite write serialization, recognizes the same
   Command ID/digest replay only with fresh authority, requires the next
   contiguous sequence and strictly newer fencing token, consumes the JTI, and
   appends the command and state/event changes atomically.
3. A Cancel command records `cancel_requested`; it is not cancellation proof.
   Execution-loop stop or reconciliation runs outside the transaction. A later
   transaction records immutable cancellation evidence, appends
   `runtime.run.cancelled`, and makes `cancelled` terminal.
4. Checkpoint creation serializes private state outside the database transaction
   into a content-addressed temporary object, verifies digest/size, atomically
   renames the object, then appends manifest and event facts. A failed database
   commit may leave an unreferenced object eligible for safe garbage collection,
   but no committed manifest may reference missing content.
5. Restore verifies exact ProviderRevision, Runtime revision, checkpoint digest,
   size, event sequence, compatibility profile, and content before dispatch.
   `compatible_revision` and `portable` fail closed in B03.2a.
6. Event reads return `event_sequence > after_event_sequence` in strict order.
   Retention may advance only after a usable checkpoint exists. An older cursor
   returns explicit 410 recovery details and does not silently reset to zero.
7. No HTTP, key lookup, filesystem serialization, execution-loop call, or other
   external work occurs inside the SQLite transaction.

## Go AgentRuntimeProvider Port And HTTP Adapter

The Go Port exposes stable Platform values and typed outcomes without leaking
generated transport, `net/http`, Provider-private checkpoint content, or native
Runtime IDs. The adapter consumes an already resolved immutable endpoint/TLS
binding and already issued Runtime token. Until B03.2b supplies those authorities,
only component and integration harnesses may construct the adapter.

The adapter must:

- use an injected bounded `http.Client`, exact TLS trust and client identity,
  disabled redirects, per-operation deadline, and bounded response reader;
- serialize generated transport deterministically, bind path/query/body to the
  requested operation, and set no caller-controlled endpoint or Host override;
- require exact success status and content type, reject unknown response fields,
  validate response identity and monotonic state/cursor values, and validate
  every Provider event against the admitted Registry binding;
- never retry Start or Command internally; retry policy and reconciliation
  belong to the durable caller;
- keep Capabilities immutable per ProviderRevision and fail closed on drift;
- retain StandardError code/details for diagnostics while mapping to a closed
  domain error class.

### HTTP And Outcome Classification

| Provider result | Read operation | Mutation operation |
|---|---|---|
| 400 | invalid request | known rejection |
| 401 | authentication rejected | known rejection |
| 403 | authority/binding rejected | known rejection |
| 404 | RuntimeRun not found | known rejection |
| 409 | protocol/state conflict | known digest, sequence, or fencing rejection |
| 410 | cursor expired with recovery path | not applicable |
| 413 | not applicable | known pre-parse size rejection |
| 422 | unsupported operation/checkpoint | known rejection |
| 429 plus valid Retry-After | bounded retryable read failure | known throttling; caller decides a fresh authorized attempt |
| 500 or 503 | retryable/unavailable read failure | `outcome_unknown` |
| timeout, reset, invalid/truncated response, identity mismatch | read failure | `outcome_unknown` |

Provider `retryable` text cannot convert an uncertain mutation into a known
failure. A 202 Cancel response with `cancel_requested` proves acceptance only.
Terminal cancellation requires a conforming Provider status/event or later
Platform reconciliation evidence. A late response with stale fencing cannot
advance Platform state.

## B03.2c Fenced System Cancel Integration

B03.2c begins only after B03.2b and production Safety Controller admission are
available. Its minimum durable sequence is:

1. The authenticated Safety Controller admits immutable trigger evidence and,
   in one PostgreSQL transaction, appends SystemSafetyControl, newly fenced
   RuntimeCommand, complete target/Fanout facts, and Outbox intent.
2. A leased dispatcher consumes the committed Outbox and signals an already
   confirmed WorkflowRun. It must never use Signal-with-Start or create a
   Workflow from a control message.
3. The versioned Workflow receives only bounded command IDs/digests and schedules
   an Activity. Tokens, endpoints, request content, and Provider responses do not
   enter Workflow History.
4. The Activity first commits an InvocationAttempt prepared/dispatch fact, then
   calls the Go Runtime Port outside every PostgreSQL transaction.
5. A known rejection or conforming response is committed in a second transaction.
   Network uncertainty records `outcome_unknown` and opens/reuses a durable
   ReconciliationCase; it never reports failure or retries the same mutation
   token implicitly.
6. Reconciliation obtains fresh Status/Event safety-control authority, compares
   fencing, command and event evidence, and resolves to running, succeeded,
   failed, cancelled, a new authorized retry, or ManualReview.
7. `cancel_requested` or command acceptance progresses a target only to
   dispatched. Provider cancellation evidence and the admitted CanonicalEvent
   transaction are required before RuntimeRun/Fanout becomes confirmed or
   cancelled.
8. A prior success/failure racing with Cancel remains that terminal result; an
   older response cannot overwrite the higher fencing owner.

Changing the B03.1 Workflow requires a new admitted Worker Build ID, retained old
workers, bounded History inputs, real Temporal recovery tests, and Replay of all
accepted histories before activation.

transitions, sequence/fencing, idempotency conflict, JTI replay, event typing,
cursor retention, checkpoint digest/compatibility, and error classification.

Component evidence shall use a built Native Runtime artifact and real process
boundary with:

- an ephemeral CA, server certificate, permitted and rejected client identities;
- real EdDSA and ES256 signatures, wrong algorithm/type/key/audience/caller,
  expired/not-yet-valid/overlong tokens, key rotation, stale fencing, and
  mutation JTI replay;
- a real SQLite file and checkpoint directory, forced transaction failures,
  process termination before/after commit, response loss, restart, and recovery;
- a real Go HTTP adapter under normal and Race tests, bounded concurrency,
  response truncation, invalid content type/body, 429/500/503, and redirect
  rejection;
- dynamic reading of the exact locked Suite, exact case-ID coverage, Contract
  fixture validation, Registry payload validation, and explicit per-case verdicts.

Generated evidence must bind Blueprint and Contract source digests, Contract
Manifest and Suite digests, generator/runtime dependency locks, source-tree and
generated-tree digests, Native Runtime artifact, Go adapter source, Provider and
Runtime revisions, capabilities and Event Registry digests, commands, logs,
test certificates/keys as non-secret test identities, checkpoint artifacts, and
all pass/fail summaries.

Mocks may support unit error paths but cannot prove TLS/JWS, body-limit handling,
SQLite commit/restart, filesystem checkpoint atomicity, HTTP uncertainty,
process restart, or cross-language adapter behavior. B03.2b/c later require real
PostgreSQL and Temporal evidence; B03.2a component evidence cannot substitute
for them.

Only complete `phase0_implementation_required` responsibilities may be added to
the traceability map. A Suite case count, generated DTO, README, local string
check, or administrator-seeded safety parent is not an implementation claim.

## Rollback Classification

- P0 generator and dependency changes are reversible only as one locked unit:
  tool versions, generated code, Python lock, Go modules if any, third-party
  inventory, SBOM/provenance, and Gate expectations roll back together.
- An empty Provider-local store may support tested Down/Up. Once Run, JTI,
  command, event, or checkpoint facts exist, destructive rollback is refused;
  use a reviewed forward migration or a proven old-reader compatibility path.
- Provider rollback activates a prior immutable ProviderRevision and Runtime
  revision. It never changes capabilities under an existing revision or routes
  an existing Run to an incompatible implementation.
- Checkpoint objects are retained while any manifest or reconciliation case can
  reference them. Rollback never deletes or reinterprets checkpoint content.
- Go adapter rollback is code-only while it remains unwired; after production
  wiring it must preserve every admitted wire/error classification.
- B03.2b PostgreSQL migrations are expand-only. Empty new tables may support a
  tested Down; data-bearing authoritative tables are forward-only.
- B03.2c Worker rollback retains old Build IDs and Workflow code until Replay
  proves compatibility for every retained history. Temporal persistence is
  never downgraded in place.
- Safety rollback may stop new dispatch but must leave response processing and
  reconciliation active. It cannot delete SystemSafetyControl, RuntimeCommand,
  Outbox, Attempt, Event, or terminal evidence.
- Verification keys remain available for the maximum 300-second token lifetime,
  admitted clock skew, and all in-flight verification windows.

## Activation And Evidence Tiers

Completion and activation remain separate:

1. Contract Gate proves the locked Contract itself and generated projection.
2. Component evidence proves Native Runtime and Go adapter behavior.
3. Cross-component evidence proves the real HTTP/TLS/process boundary.
4. Platform integration evidence proves PostgreSQL, Temporal, Outbox, authority,
   reconciliation, and CanonicalEvent transactions.
5. Reliability evidence proves repeated crash, race, lease, clock, key rotation,
   capacity, and recovery behavior.
6. Formal freeze, security approval, deployment approval, and production evidence
   require their own owners and are not inferred from earlier tiers.

No production composition root may wire the Runtime adapter, Runtime Start,
Outbox dispatcher, Safety Controller, or new Workflow signal until its exact
authority slice and activation evidence are approved.

## Explicitly Unproven Boundaries

Even after B03.2a completes, the following remain unproven:

- complete `runtime-core-v1` Conformance and its four platform-dependent cases;
- production ProviderResolution, endpoint trust, capability admission, token
  issuer, signing-key custody, rotation, revocation, and workload identity;
- production WorkOrder/Workflow/Runtime Start authority and atomic Start Outbox;
- complete RunManifest, RootBinding, RuntimeAuthorization, ArtifactGrant,
  Invocation, ReconciliationCase, and ManualReviewDecision persistence;
- CanonicalEvent/Registry/Inbox persistence and Provider Event projection;
- production Platform Safety Controller and trigger-evidence admission;
- fenced System Cancel dispatch, race resolution, terminal aggregation, and
  externally visible cancellation event;
- cross-revision checkpoint compatibility or portability;
- model/tool/artifact/credential/egress Gateway behavior, real Agent Loop,
  Sandbox, Usage, child Agent, background tasks, and Workbench projection;
- production server topology, Payload encryption, capacity, backup, disaster
  recovery, multi-region behavior, Phase 0B completion, 0H reliability, formal
  freeze, security approval, or production readiness.

If implementation cannot prove an identity, authority, transition, digest, or
transaction from the locked Contract and admitted parents, the affected work
stops. It must not be repaired with an unconstrained string, pseudo-foreign key,
test-only shadow model, copied Contract resource, private Platform Event, or
Contract modification.
