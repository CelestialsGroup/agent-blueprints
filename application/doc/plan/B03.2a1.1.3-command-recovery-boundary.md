## B03.2a1.1.3a Command HTTP Boundary

### 1. 动态 route 与 request target

新增 Command route-aware request-line 判定和动态 `runtime_run_id` 提取：

- 只接受 `POST /v1/runs/<runtime_run_id>/commands HTTP/1.1\r\n` origin-form；
- 固定 prefix/suffix 和中间 path segment 必须按 wire bytes 精确匹配，不进行 percent-decode、
  Unicode normalization、dot-segment normalization 或 slash collapsing；
- 拒绝 absolute-form、authority-form、asterisk-form、query、fragment、空 segment、额外 `/`、
  `\\`、`%` 编码替换、控制字符和路径后缀；
- path runtime_run_id 与 JSON body、token claims 中的 runtime_run_id 必须分别验证并完全一致；
  任何一个都不能代替另一个；
- 非精确 method/path 不落入 Command handler，不重定向，也不把 Status/Event route 误接线；
- route-aware request concurrency exhausted 映射为 Command OpenAPI 的 429，而非通用 503。

### 2. Host、Content-Type 和 framing

复用 a1.1.2 的 bounded HTTP server，但为 Command route 独立证明：

- 唯一、canonical、与 immutable process configuration 一致的 Host；
- 唯一且逐字节为 `Content-Type: application/json`；
- 恰好一个 `Content-Length`，只接受非空 ASCII 十进制、无符号、无前导零、无逗号合并、
  无 OWS 变体和有界 digit count；
- 任意 `Transfer-Encoding` 均拒绝，包括 `chunked` 和 identity；
- 任意 `Expect` 均拒绝，包括 `100-continue`；
- 重复 Content-Length、代理合并值、CL/TE 共存、缺失 CL 和其他歧义 framing 均 400；
- framing 失败后关闭连接，不读取或解释可疑剩余字节，不允许 request smuggling 到下一请求。

### 3. 262144-byte pre-parse admission

Contract `x-max-encoded-body-bytes=262144` 是 encoded request body 的硬上限：

- `Content-Length > 262144` 时，在读取 body、Bearer/JWS、JSON、Schema、SQLite 前发送 413
  并关闭连接；
- 精确 262144 bytes 进入正常解析，262145 bytes 必须稳定 413；
- exact-body reader 使用整次 body 的绝对 deadline，不允许每个 chunk 重新获得完整 timeout；
- 覆盖多 chunk slow body、声明长度大于实收的 short read、TLS half-close、read timeout、
  client reset 和 body 后多余 bytes；
- short read、half-close、timeout 或连接状态已不允许安全响应时只关闭连接；若仍可安全发送，
  必须发送通过 StandardError 的 400/503，且两种路径都为零 store 访问；
- 所有退出路径释放 request slot，更新有界 metrics，不在日志记录 body 或 Authorization。

### 4. Bearer、mTLS 和 Secure Admission Core

Command handler 必须：

1. 只接受一个 `Authorization` header 和精确 `Bearer <compact-jws>`；
2. 在解码前限制 token 总 bytes 和三个非空 base64url segment；
3. 将 mTLS 证书解析出的唯一 `token_subject` 原样传给 Secure Admission Core；
4. 预期 profile 固定为 `submit_command`，不根据不可信 header/claim 动态选择 validator；
5. 验证 typ/kid/alg、EdDSA/ES256 signature、issuer、audience、sub、iat/nbf/exp/JTI、
   Provider revision、operation Contract/Profile；
6. 验证 token `sub` 精确等于 certificate identity；
7. 验证 token operation 为 `submit_command`，operation request digest 等于 Command
   self digest；
8. 验证 path/body/token runtime_run_id、Invocation、Attempt、sequence、fencing、authority
   mode、SSC ID/digest 和 command deadline/time window；
9. 完成上述 cryptographic admission 后才允许进入 store transaction 核对 Provider-local
   durable security binding；
10. 不允许 audience、path ID、body ID、digest、Invocation/Attempt、sequence、fencing 或
    durable binding 互相替换或补齐。

当前 `_command_mutation` 会在 JWS verify 前拒绝不支持的 Command type。实施时必须把
“解析完整通用 Command context”和“构造 Provider-supported mutation”分开：所有 Contract
variant 先完成 Schema/self-digest/path/JWS/request-context admission，再决定接受或返回 422。
这项重构不得触发 store read，也不得为不支持的 variant 创建局部事实。

### 5. 404 oracle 与 durable transaction

- malformed/invalid Bearer、JWS Header/Claims、signature、issuer/audience/sub、time、operation、
  request digest 和 presented context 对存在或不存在的 RuntimeRun 必须产生相同 pre-store
  拒绝；
- 只有完成 cryptographic admission 的请求才可进入 SQLite transaction；
- 404 只表示一个 cryptographically admitted target 在 Provider-local store 不存在；
- 对已存在 RuntimeRun，durable binding 核对和 Command mutation 必须在同一事务中完成，
  不得先读取状态后在另一事务授权；
- binding mismatch 返回 403，不暴露哪一个 Tenant/Run/Manifest/Authorization/Policy/Budget/
  Permissions/Invocation/Fencing 字段不匹配；
- 错误、日志和 evidence 不记录 Runtime token、Command body、checkpoint 内容、private key、
  SQL row 或内部异常文本。

### 6. Command variant 权威矩阵

| Contract variant | 当前 Provider-local 决定 | 状态、work、event 边界 |
|---|---|---|
| `pause` | 接受 execution + `authorized_control_request_id`，或 safety token + 精确 SSC ID/digest；两种 authority 必须互斥 | 仅从 `running` 同步进入 `paused`；不创建 work，不虚构 Event |
| `resume` | 仅接受 execution + `authorized_control_request_id`；拒绝 safety authority | 仅从 `paused` 同步进入 `running`；不创建 work/Event |
| `cancel` | 接受 execution control 或 safety control 两种互斥 authority | 202 只进入 `cancel_requested` 并创建一个 cancel work；真实 execution evidence 后才可 `cancelled` 并发取消事件 |
| `checkpoint` | 仅接受 execution authority；不得包含 ControlRequest 或 SSC | 202 保持当前允许状态并创建一个 checkpoint work；manifest/event 只在 worker 成功后同事务提交 |
| `append_input` | 完整 Schema/JWS/context admission 后明确 422 | 缺少可核对的持久 ControlRequest/input authority；零 JTI/Command/work/event |
| `interrupt` | 完整 admission 后明确 422 | 缺少可核对的持久 ControlRequest/input authority；零事实 |
| `approval_decision` | 完整 admission 后明确 422 | 不发明 Approval 或 ControlRequest 父事实；零事实 |
| `subagent_spawn_decision` | 完整 admission 后明确 422 | 需要平台 Child Admission/allocated AgentRun authority；不创建影子事实 |

422 只表示 Schema-valid、cryptographically admitted 请求超出当前 Provider 能力，不表示相应
平台父事实不存在或存在。未来若实现这些 variant，必须先获得相应 authority slice 的独立计划
和批准。

### 7. Command 原子语义

保留并从 HTTP 真实进程验证：

- fresh JTI + same command ID + same digest 是成功 replay，消费 fresh JTI，返回相同 accepted
  Command 派生状态，不重复 Command/work/event；
- 相同 JTI replay 为 409，不能创建或改变事实；
- same command ID + different digest、same idempotency key + different Command 为 409，fresh
  JTI 不得被消费；
- 新 Command sequence 必须等于 `last_command_sequence + 1`；gap、duplicate 或 reverse 为 409；
- 新 fencing 必须严格大于 observed fencing；stale/equal fencing 为 409；
- 并发 Command 由真实 SQLite transaction 串行化，只有满足 sequence/fencing 的请求接受；
- Command deadline 必须未过期，token expiry 不得越过 Command deadline 或已绑定的 durable
  authorization/policy/budget 上界；
- authority mode、ControlRequest ID、SSC ID/digest 必须满足 Contract 和既有 kernel 约束；
- terminal state、非法 Pause/Resume/Cancel/Checkpoint transition 为 409；
- `cancel_requested` 仅证明接受；没有真实 completion evidence 时严禁提升为 `cancelled`；
- Pause/Resume 不新增 Event；Checkpoint accepted 不新增 manifest/Event；这些行为只能由锁定
  Contract 和既有 kernel 决定，不能为 HTTP 便利改写。

### 8. 封闭 HTTP 响应映射

| HTTP | 封闭类别 | 约束 |
|---|---|---|
| 202 | Command accepted/replayed | body 先通过 AgentRuntimeRunStatus；Content-Type/Length canonical 且不超过 response limit |
| 400 | request-line/framing/content type、Strict JSON、Schema、自摘要、deadline 或 malformed presented body | 不泄露具体 token/body/internal field |
| 401 | missing/malformed Bearer、JWS Header/Claims/signature/issuer/audience/sub/time/operation rejection | 存在/不存在 run 行为相同且零 store access |
| 403 | cryptographically valid token 与 certificate/request/durable binding/authority 不匹配 | 不泄露 durable field 或 run existence before admission |
| 404 | cryptographically admitted RuntimeRun 在 Provider-local store 不存在 | 仅在 crypto admission 后产生 |
| 409 | JTI/idempotency/digest/sequence/fencing/state/concurrency mutation conflict | 不自动重试 Command |
| 413 | encoded body 超过 262144 | JSON/Schema/JWS/SQLite 前失败 |
| 422 | 完整 admission 后的 unsupported Contract variant/Provider semantics | 零 durable facts |
| 429 | Command request concurrency limit | Schema-valid StandardError、`Retry-After`、连接关闭策略明确 |
| 500 | response Schema/size failure或归一化未知内部错误 | 只发送固定 StandardError；绝不发送 traceback |
| 503 | not-ready/draining、SQLite BUSY/LOCKED 或可安全响应的临时 I/O/read failure | retryable/`Retry-After` 与现有 process policy 一致 |

所有可发送错误必须先通过锁定 StandardError validator。若 StandardError 本身无法在
`max_response_bytes` 内安全编码，只关闭连接。成功 response 也必须在 write 前完成 Schema、
byte limit、Content-Type 和 canonical Content-Length 检查；write timeout/half-close 不进行
mutation retry。

## B03.2a1.1.3b Transaction SIGKILL And SQLite Reopen

### 1. 可测事务边界

禁止在生产 handler、core 或 store 加入“在某阶段 sleep/raise/kill”的 fault hook。若为了
确定性证明必须拆分现有单体调用，只允许把真实 production transaction 重构成：

- 完整 pre-store Command admission value；
- 接收真实 `sqlite3.Connection` 的同一 production transaction body；
- production wrapper 负责 begin/commit/rollback；
- 安装 wheel 后的 test driver 可以用同一 transaction body 和真实 connection，在事务外部
  stdout flush 一个不含秘密的阶段 marker，再由父测试进程发送 SIGKILL。

test driver 位于 test source，不进入 wheel console scripts；不得复制 SQL 或重新实现 store
语义。若不能让生产路径和 test driver 调用同一 transaction body，就停止 1.1.3b，不用
monkeypatch `commit`、`execute` 或 context manager 冒充。

### 2. 必测故障窗口

1. 完成 JSON/Schema/JWS/request context 后、开启 transaction 前 SIGKILL：重启后 JTI、
   Command、run status、sequence、fencing、work、event 全部不变。
2. transaction 中已写入 JTI/Command/state/work 但 commit 前 SIGKILL：真实 SQLite reopen
   后全部回滚，不出现消费但无 Command、Command 但无状态或 pending work。
3. commit 完成后、调用方获得 response 前 SIGKILL：使用 installed transaction driver 在
   commit 后、输出结果前被杀，同时用真实 HTTP client response loss case补充 transport
   证据；重启后 committed facts 完整可见。
4. 对第 3 类使用同 Command/digest/idempotency 和 fresh JTI 重试：返回同一状态，最终一个
   Command、一个对应 work、零或 Contract 允许的唯一 Event，并记录两个 accepted JTI。
5. 每个窗口都关闭旧进程，使用新 installed-wheel process 执行 `open_current`/reopen；
   `serve` 不迁移、不修复或删除事实。

父进程必须用 `os.kill(pid, signal.SIGKILL)` 并核对负 signal return code；graceful SIGTERM、
Python exception、socket close 或测试进程自行退出只能作为补充证据，不能标注为 kill -9。

## B03.2a1.1.3c Installed Test Worker Lease Recovery

### 1. worker ownership 边界

当前生产 `agent-native-runtime-serve` 只有 transport/process composition，没有 execution
worker。此子切片只新增 test-only installed worker/driver：

- 测试先可复现构建并安装 wheel；
- worker 从安装位置导入真实 `NativeRuntimeKernel`、store 和 execution protocol；
- worker 只在测试目录中启动，不新增 console script、后台 thread、container 或生产配置；
- execution fixture 只提供确定性的测试可观测结果，证明范围限于 Provider-local lease、
  fencing、durable completion；不据此声明生产 executor 或外部 side effect exactly-once；
- 如果真实 recovery 必须把 worker 接入 `serve` 或新增生产 composition root，立即停止
  1.1.3c，并把生产 worker ownership 记为 authority gap。

### 2. 真实 lease 时序

至少对 cancel 和 checkpoint work 分别覆盖：

1. owner A 用 installed worker 获取真实 SQLite lease，stdout flush `work_id`、owner、
   lease token 和持久 `lease_expires_at` 的非秘密摘要；
2. 父进程确认 DB 已为 `processing` 后 SIGKILL owner A，确保其没有执行 release path；
3. 在持久 `lease_expires_at` 前由 owner B claim，必须返回无 work；
4. 使用真实墙钟等待到 expiry，并以小步 bounded poll 和总 timeout 获取；不得注入 fake clock；
5. owner B reclaim 同一 work，lease token/fencing 必须严格增加；
6. 用 owner A 捕获的旧 lease identity 调用真实 completion/release，必须
   `WorkLeaseLostError`，不能修改状态、event 或 work；
7. owner B 完成一次后，重复 completion 和第三 owner claim 都不能重复结果；
8. reopen 后核对同一 RuntimeRun 只有一个 Command、一个 durable work completion、一个
   checkpoint/cancel completion Event（若该 work 成功完成），sequence 连续且 fencing 单调。

时间证据记录配置 lease duration、DB UTC expiry、父进程 monotonic timestamps、到期前检查和
到期后 reclaim 时间。不得用宽松 sleep 断言；若 CI/容器时钟无法在明确 margin 内稳定证明
边界，停止该证明并修复 harness，不能降低 assertion。

## B03.2a1.1.3d Checkpoint Crash Consistency

### 1. production writer 重构边界

现有 checkpoint writer 必须在不改变 content-addressed identity 的前提下重构成生产连续调用的
明确步骤：

1. 校验 payload byte limit，确定 SHA-256 digest、size 和 target path；
2. 在受限 tmp directory 以 `O_CREAT|O_EXCL` 和 0600 创建并写入 temp object；
3. flush 并 `fsync` temp file；
4. 对已存在 target 验证 digest/size，或以 atomic rename/replace 发布；
5. `fsync` target directory，确保 rename 的 directory entry 持久化；
6. 构造 `portability=same_revision` manifest；
7. 在真实 SQLite transaction 中原子提交 manifest row、RuntimeRun checkpoint、
   `runtime.checkpoint.created` Event 和 work completion。

production path 顺序调用这些步骤，不接收 fault-point 参数或 callback。installed test driver
只能在调用真实步骤之间 stdout flush marker 并等待父进程 SIGKILL；不得 monkeypatch
`os.fsync`、`os.replace`、SQLite commit 或 `CheckpointObjectStore.write`。

### 2. crash matrix 与恢复不变量

外部 SIGKILL 至少发生在：temp 部分写入后、完整写入但 file fsync 前、file fsync 后、rename
后 directory fsync 前、directory fsync 后 manifest transaction 前、manifest/event 写入后
commit 前、manifest commit 后 response/result 前。

每个 case 以新 installed-wheel process `open_current` 后核对：

- temp/未引用 content-addressed object 可以成为 orphan；本切片不删除或回收它；
- 已提交 manifest 必须引用存在的 object，且 `read_verified` 的 digest/size 完全匹配；
- 禁止 committed manifest 引用缺失、部分、未 fsync 或 digest 不符的内容；
- manifest row、RuntimeRun checkpoint、checkpoint Event 和 work completion 要么全部提交，
  要么全部回滚；
- crash 后重试同一 work 不得产生第二个 manifest/Event/work completion；
- restore 只验证相同 ProviderRevision、runtime revision 和 compatibility profile；
- cross-revision `CompatibilityDecision`、portability、升级/降级恢复继续明确排除。

## 停止条件与权威缺口

以下任一情况立即停止受影响范围，并在本文阶段台账记录实际证据、未完成项和 rollback：

- 开始阶段时 HEAD/branch/worktree 或锁定 Blueprint/Contract/Manifest/Suite/projection digest
  与批准基线不符且未经重新审计；
- 必须新增第三方依赖，或必须修改 Blueprint/Contract 才能实现目标；
- Host/framing/Bearer/body limit/Schema/JWS/certificate/request context 任一必要验证无法在首次
  store 访问前完成；
- Command OpenAPI 状态无法封闭映射；不得借此解释 Status/Event HTTP 400；
- unsupported variant 无法在完整 cryptographic admission 后、store 前安全拒绝；
- response 无法通过 AgentRuntimeRunStatus，错误无法通过 StandardError，或调试要求泄露
  token/body/checkpoint/private key/internal exception；
- mutation JTI 与 accepted facts、fresh-JTI replay、digest conflict、sequence/fencing 或状态
  语义无法保持既有事务原子性；
- transaction、lease 或 checkpoint recovery 只能通过 mock、fake clock、monkeypatch、
  graceful exception 或 production fault hook 证明；
- 真实 lease/checkpoint recovery 必须新增生产 worker、composition root/container、平台 caller
  或未授权 execution ownership；
- 必须新增 Go adapter、ProviderResolution、token issuer/private-key custody、平台 PostgreSQL/
  Temporal caller、CanonicalEvent 或生产 Safety Controller；
- committed checkpoint manifest 可能引用缺失或未持久化内容；
- 完整 `make validate-implementation` 任一既有 Gate 回归且不能在本切片内修复；
- 真实时序或 SIGKILL harness 不能可重复证明所声明窗口，只能依赖宽松 sleep 或概率成功。

当前持续存在的 authority gaps：生产 Provider admission/endpoint trust、certificate registration、
token issuance、ControlRequest/SSC/Approval/Child Admission 父事实真实性、生产 worker/executor、
external side-effect reconciliation、CanonicalEvent、Safety Controller、Go adapter、Status/Event
400 解释和 cross-revision checkpoint compatibility。本文只能证明呈现请求、token 与
Provider-local durable facts 的一致性。
