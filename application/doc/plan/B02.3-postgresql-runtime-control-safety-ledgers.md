## Implemented Bounded Scope

The implemented slice adds:

- Tenant-qualified, append-only SystemSafetyControl facts with exact persisted
  scope, issuer/evidence references, digest idempotency, reduction-only action
  enforcement, and a fail-closed external authority-verification port;
- append-only AgentRuntimeCommand sequencing, idempotency, authority
  exclusivity, invocation binding, and monotonically increasing fencing;
- versioned AgentRunControlFanout snapshots with immutable authority and target
  identity, per-target fencing, monotonic progress, bounded leased claims,
  crash recovery, and reconciliation state;
- atomic Outbox writes whose Message ID, payload digest, fixed destination,
  availability time, and creation time are bound by PostgreSQL foreign keys and
  local checks; the exact Platform Event transaction is deferred until
  CanonicalEvent admission is available;
- domain-valued repositories that expose atomic use cases and do not leak
  pgx/sqlc rows.

## State Machines And Transaction Boundaries

The implementation must preserve these boundaries without restating their
upstream definitions:

1. Before a safety-control transaction begins, an injected control-plane port
   must authenticate and validate the issuer/evidence relationship; absence or
   rejection fails closed. The transaction then resolves the persisted
   WorkOrder/RuntimeRun, trigger evidence, and controller reference before
   appending one SystemSafetyControl and its Outbox intent atomically. A system fanout also
   allocates the target fencing and appends each control, command, control
   Outbox, command Outbox, target, and version-one snapshot in that transaction.
2. A command transaction locks its RuntimeRun sequence/fencing owner, resolves
   exactly one permitted authority source for the command type, verifies the
   logical Invocation/Attempt, appends the next command and its Outbox intent,
   and treats the same ID/digest as replay while rejecting digest conflict.
3. A fanout acceptance transaction closes later Child admission, locks the
   WorkOrder and every active AgentRun/RuntimeRun target, resolves exactly one immutable authority,
   persists the accepted active-work CAS version, allocates distinct target
   fencing values and system controls where required, and appends version one
   plus command/control Outbox facts atomically.
4. Fanout workers claim bounded target work with `FOR UPDATE SKIP LOCKED`, lease
   and fencing, commit before network I/O, then append a contiguous snapshot
   version with exact predecessor digest. Progress cannot regress; stale or
   expired owners cannot mutate a newer claim.

Authority admission copies, validates, and bounds each input batch, then
prelocks the deduplicated WorkOrder set in global ID order before inserting any
child fact. Each fact category also has a stable parent/identity order;
Invocation attempts sort by Invocation ID, attempt number, and Attempt ID. The fanout lock order is WorkOrder,
immutable active AgentRun membership,
matching locked RuntimeRun target set, then individual command cursor. Database
admission guards take the same WorkOrder lock and reject new Run or accepted
Child Admission facts after Fanout acceptance, so membership cannot change
around the snapshot without granting UPDATE on immutable AgentRun rows. A late
spawn may still append an immutable rejected decision. Progress locks the fanout
root before all target rows. Transactions contain no network I/O.

## Migration And Rollback Classification

Migration `00003` is expand-only and creates the approved direct parents before
the leaf ledgers in dependency order. Empty B02.3 tables are eligible for a
reviewed Down/Re-Up; once any authoritative control,
command, fanout version, target, or claim exists, destructive Down must refuse
and recovery must use a reviewed forward migration. Dependency/tool rollback
restores exact prior pins and regenerated sqlc output, then reruns the complete
real-PostgreSQL Gate. The additive Outbox `initial_available_at` column remains
across an empty Down so the current binary can still read B02.2 rows at migration
version 2; B02.3 constraints are removed and a repeated Up reuses the column.
PostgreSQL data directories are never downgraded in place.

- WorkOrder plus WorkOrderControlRequest/ControlInput and active-work/admission
  state for user controls and fanout authority;

ID registries. Each admitted parent fact needs explicit lifecycle bounds,
migration/rollback classification, and real PostgreSQL integration evidence.

## Unproven Boundaries

The locked AgentRuntimeCommand Schema does not bound several identifiers that
this PostgreSQL slice stores in indexed `varchar(200)` columns, including
Command, RuntimeRun, Approval, Invocation/Attempt, and Idempotency identities.
SystemSafetyControl's `evidence_contract_id` is pattern-bounded but has no
maximum length. The schemas also permit some JSON identifier strings containing
U+0000, which PostgreSQL text cannot represent. Application rejects values over
200 runes and U+0000 fail closed;
that is a deliberate implementation subset, not complete Contract conformance.
Changing the Contract or inventing an unbounded pseudo-key is outside B02.3.

This slice does not prove authoritative safety evidence/controller admission,
the production SystemSafetyAuthorityVerifier, Canonical Platform Event
atomicity, complete parent lifecycles, ExecutionGrant consumption or external
WorkOrderControlRequest intake, Business revocation intake, Runtime HTTP/token
behavior, Provider Conformance, a Runtime side effect, WorkOrder terminal
aggregation, end-to-end execution, Phase 0B, reliability approval, freeze,
security approval, or production readiness. The Canonical source PostgreSQL
representation gap recorded by B02.2 remains unchanged.
